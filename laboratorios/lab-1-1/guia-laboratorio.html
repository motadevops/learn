Laboratorio 1.1: el servicio que no responde

Un entorno real con cuatro máquinas que fallan de formas distintas. Con tus propias herramientas vas a distinguir un rechazo, un silencio, un camino roto y un error de aplicación, y vas a comprobar con una captura de red todo lo que vimos en teoría.

Objetivo Arquitectura Requisitos Archivos Paso a paso Pruebas Errores Limpieza Ejercicio
1. Objetivo

Qué vas a lograr

Al terminar, vas a poder hacer cuatro cosas con evidencia propia: leer una tabla de rutas y una tabla ARP de un sistema real, demostrar con una captura de tráfico que la MAC destino de un paquete es la del gateway, distinguir refused, timed out y no route to host por su causa real, y encontrar y corregir un servicio que está sano pero inaccesible.

Tiempo estimado: entre una hora y media y dos horas, sin contar el ejercicio individual. Es seguro: no hay comandos destructivos. Todo ocurre dentro de una red aislada de Docker.

Importante: yo preparé y validé la sintaxis de los archivos, pero no los ejecuté en tu máquina. Todo lo que yo describa en "Qué debes observar" es lo que debería ocurrir según cómo funciona el sistema. Lo que realmente veas en tu pantalla es lo que cuenta, y si no coincide, eso es información valiosa para el diagnóstico.

3. Arquitectura

El entorno

Una red de Docker con la dirección 172.21.0.0/24. Desde client vas a diagnosticar a las otras tres máquinas. Cada una falla de una manera distinta. La IP 172.21.0.99 no pertenece a nadie, a propósito.

Verde: sano. Rojo: rechaza (refused). Amarillo: silencio (timeout). Punteado: sin camino. El gateway es el puente que Docker crea en tu máquina.

4 y 7. Requisitos e instalación

Qué necesitas

  • WSL2 con Debian y Docker Engine funcionando, con Docker Compose (comando docker compose).
  • Visual Studio Code, opcional pero recomendado.
  • Conexión a internet la primera vez, para descargar la imagen base de Debian y sus paquetes.
  • Unos 400 MB de espacio libre.

No hay que instalar nada en tu WSL. Las herramientas de diagnóstico (tcpdump, nc, dig, ip) se instalan dentro de la imagen del laboratorio mediante el Dockerfile. Eso mantiene tu sistema limpio y hace que el laboratorio sea reproducible.

entrypoint-fw.sh

Instala el firewall que descarta paquetes y arranca el servidor de fw.

Archivo: entrypoint-fw.sh
#!/bin/sh
# Arranque del servicio "fw".
# Primero instala una regla de firewall que DESCARTA en silencio los paquetes TCP
# que llegan al puerto 9090, y despues arranca un servidor web en ese puerto.
# Resultado: el servicio esta vivo y escuchando, pero desde fuera nadie le llega.
# Es el origen de un "connection timed out".
set -e

PORT=9090

if iptables -A INPUT -p tcp --dport "$PORT" -j DROP 2>/dev/null; then
  echo "[fw] regla DROP instalada para el puerto $PORT (iptables)"
elif command -v iptables-legacy >/dev/null 2>&1 \
     && iptables-legacy -A INPUT -p tcp --dport "$PORT" -j DROP 2>/dev/null; then
  echo "[fw] regla DROP instalada para el puerto $PORT (iptables-legacy)"
else
  echo "[fw] ERROR: no se pudo instalar la regla de firewall." >&2
  echo "[fw] El kernel o los permisos del contenedor no lo permiten." >&2
  exit 1
fi

exec python3 -m http.server "$PORT" --bind 0.0.0.0 --directory /srv

# Muestra en una tabla todo lo que hay en el laboratorio 1.1:
# contenedores, para que sirve cada uno, su IP, su puerto, su red y sus volumenes.
# Solo lee informacion de Docker. No cambia nada.
#
#   bash info.sh

LAB="1.1"

echo "== Laboratorio $LAB: contenedores =="
echo

fmt="%-24s %-12s %-14s %-9s %-10s %-9s %s\n"
printf "$fmt" "CONTENEDOR" "ESTADO" "IP" "PUERTO" "RED" "VOLUMENES" "ROL"

verify.sh

Comprueba automáticamente todos los resultados del laboratorio.

Archivo: verify.sh
#!/usr/bin/env bash
# Verificacion automatica del laboratorio 1.1.
# Ejecutalo desde la carpeta del laboratorio, con el entorno levantado:
#
#   bash verify.sh            estado inicial (la api falla a proposito)
#   bash verify.sh --fixed    despues de arreglar la api
#
# Cada prueba lanza un comando desde el contenedor "client" y comprueba que el
# resultado contenga lo esperado.
#
# Para distinguir "refused", "timed out" y "no route" se usa nc (netcat), porque
# imprime el mensaje exacto del sistema operativo. El texto de errores de curl
# cambia segun su version, asi que curl solo se usa donde su salida es estable
# (codigos HTTP y resolucion de nombres).

set -u

MODE="${1:-initial}"
OK=0
FAIL=0

check() {
  # check "nombre" "patron esperado" comando...
  local name="$1" pattern="$2"
  shift 2
  local out
  out="$("$@" 2>&1 || true)"
  if printf '%s' "$out" | grep -Eqi -- "$pattern"; then
    echo "[OK]    $name"
    OK=$((OK + 1))
  else
    echo "[FALLO] $name"
    echo "        esperado (patron): $pattern"
    echo "        obtenido: $(printf '%s' "$out" | head -n 3 | tr '\n' ' ')"
    FAIL=$((FAIL + 1))
  fi
}

cl() { docker compose exec -T client "$@"; }

echo "== Modo: $MODE =="
echo

check "Escalon 1 ok: el nombre 'web' se resuelve y la web responde 200" \
  '^200$' \
  cl curl -sS -m 5 -o /dev/null -w '%{http_code}' http://web/

check "Escalon 1 falla: un nombre inexistente no se resuelve" \
  'Could not resolve host' \
  cl curl -sS -m 5 http://inexistente.lab/

check "Escalon 2 falla: la IP 172.21.0.99 no tiene camino (nadie responde al ARP)" \
  'No route to host|Host is unreachable' \
  cl nc -vz -w 10 172.21.0.99 80

check "Escalon 4 falla en silencio: fw descarta paquetes (timeout)" \
  'timed out' \
  cl nc -vz -w 4 172.21.0.30 9090

if [ "$MODE" = "--fixed" ]; then
  check "Escalon 4 ok: la api acepta conexiones en el puerto 8080" \
    'succeeded' \
    cl nc -vz -w 4 172.21.0.20 8080
  check "Escalon 5 ok: la api responde 200" \
    '^200$' \
    cl curl -sS -m 5 -o /dev/null -w '%{http_code}' http://172.21.0.20:8080/
  check "La api ya escucha en todas las interfaces (0.0.0.0:8080)" \
    '0\.0\.0\.0:8080|\*:8080' \
    docker compose exec -T api ss -ltn
else
  check "Escalon 4 falla con rechazo: la api responde 'refused'" \
    'refused' \
    cl nc -vz -w 4 172.21.0.20 8080
  check "La api escucha solo en 127.0.0.1:8080" \
    '127\.0\.0\.1:8080' \
    docker compose exec -T api ss -ltn
fi

check "Escalon 5: la aplicacion contesta 404 a una ruta que no existe" \
  '^404$' \
  cl curl -sS -m 5 -o /dev/null -w '%{http_code}' http://web/noexiste

echo
echo "Resultado: $OK correctas, $FAIL con fallo."
[ "$FAIL" -eq 0 ]
8. Implementación paso a paso

Paso a paso

Cada paso tiene tres partes: qué hacemos, por qué lo hacemos y qué pasaría si no lo hiciéramos. Cuando veas un recuadro amarillo, para y escribe tu predicción antes de ejecutar. Equivocarte en una predicción enseña más que acertar a la primera.

Usarás dos terminales. La Terminal 1 es una shell dentro del contenedor client. La Terminal 2 es otra ventana de WSL en la carpeta del laboratorio, desde la que lanzarás capturas y verás las otras máquinas.

1

Comprobar que tu entorno está listo

Qué hacemos

Verificamos que Docker, Compose y el servicio de Docker funcionan.

Por qué

Todo el laboratorio depende de que el servicio de Docker esté en marcha. Es mejor descubrirlo ahora que a mitad de un paso.

Si no lo hiciéramos

Un fallo de Docker aparecería más tarde con mensajes confusos, y pensarías que el error es del laboratorio.

WSL, cualquier carpeta
docker --version
docker compose version
docker ps
Qué debes observar

Las dos primeras imprimen versiones. docker ps imprime una cabecera, aunque no haya contenedores. Si ves "Cannot connect to the Docker daemon" o "permission denied", ve a la sección de diagnóstico de errores antes de seguir.

2

Ir a la carpeta del laboratorio

Qué hacemos

Nos situamos en la carpeta laboratorios/lab-1-1 de tu repositorio learn, donde están los archivos del laboratorio.

Por qué

Todos los comandos de Compose se ejecutan desde la carpeta que tiene el compose.yaml.

Si no lo hiciéramos

Docker Compose busca compose.yaml en la carpeta actual. Desde otra carpeta no encuentra el proyecto.

Cambia RUTA_DEL_REPOSITORIO por la carpeta donde tienes learn.

WSL, carpeta laboratorios/lab-1-1 del repositorio
cd RUTA_DEL_REPOSITORIO/learn/laboratorios/lab-1-1
ls -l
Qué debes observar

ls -l muestra el Dockerfile, el compose.yaml, los scripts entrypoint-fw.sh, info.sh y verify.sh, el README y esta guía.

3

Validar el compose antes de ejecutarlo

Qué hacemos

Pedimos a Compose que lea el archivo y compruebe que es válido, sin arrancar nada.

Por qué

Es un hábito profesional: validar antes de desplegar. Un error de sangría en YAML se detecta en un segundo.

Si no lo hiciéramos

El error aparecería a mitad del despliegue, con el entorno a medias.

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker compose config -q
Qué debes observar

Si el archivo es válido, no imprime nada. Si hay un error, indica la línea.

4

Construir la imagen y levantar el entorno

Qué hacemos

Construimos una imagen Debian con las herramientas y arrancamos cuatro contenedores: client, web, api y fw.

Por qué

--build crea la imagen la primera vez. -d deja todo en segundo plano para que puedas seguir usando la terminal.

Si no lo hiciéramos

Sin -d, la terminal quedaría ocupada mostrando logs. Sin --build, Compose no construiría la imagen la primera vez.

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker compose up -d --build
docker compose ps
Qué debes observar

La construcción tarda unos minutos la primera vez porque descarga Debian e instala paquetes. Al final, docker compose ps lista cuatro contenedores con nombres que se explican solos: lab11-cliente-pruebas, lab11-web-sano, lab11-api-solo-local y lab11-web-bloqueado. Los cuatro deben estar en marcha (Up). Si lab11-web-bloqueado aparece como salido (exited), mira sus logs con docker compose logs fw y consulta el diagnóstico.

Por qué esto y no otra cosa

Una red propia en vez de la red por defecto: en una red definida por ti, Docker ofrece resolución de nombres entre contenedores y permite fijar IP. En la red por defecto no hay resolución por nombre. Una sola imagen para todo: reduce piezas y hace el laboratorio más rápido. Servidores web de Python en vez de nginx: para TCP el comportamiento es el mismo, y evita aprender una configuración extra que aquí no aporta.

5

Leer el entorno: quién es quién

Qué hacemos

Antes de probar nada, miramos qué contenedores hay, para qué sirve cada uno, en qué red están, qué IP y puerto tienen y si guardan datos en volúmenes.

Por qué

En el trabajo, lo primero ante un entorno desconocido es inventariarlo. Por eso cada contenedor lleva un nombre que se explica solo y etiquetas con su descripción.

Si no lo hiciéramos

Sin este inventario tendrías que adivinar qué es cada contenedor por su nombre o abrir el compose a cada momento.

Antes de ejecutar, predice

¿Cuántos contenedores tendrán volúmenes? Pista: piensa si alguno guarda datos.

Primero, la vista que verás en cualquier servidor: docker ps filtrado por la etiqueta de este laboratorio y con columnas elegidas.

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker ps --filter "label=academia.lab=1.1" --format "table {{.Names}}\t{{.Status}}\t{{.Networks}}"

Después, la tabla completa con el script del laboratorio. Solo lee, no cambia nada.

WSL, carpeta laboratorios/lab-1-1 del repositorio
bash info.sh

Si quieres ver toda la configuración de un contenedor, con sus etiquetas, red, capacidades y comando:

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker inspect lab11-api-solo-local
Qué debes observar

Cuatro contenedores, todos en la red lab11-red (172.21.0.0/24). La columna VOLUMENES dice ninguno en todos: ninguno guarda datos, así que se pueden borrar y recrear sin perder nada. La sección "Qué hace cada contenedor" lee las etiquetas academia.descripcion que están en el compose.yaml.

Por qué esto y no otra cosa

Nombre de servicio corto y nombre de contenedor largo: el corto (client, api) es cómodo para escribir docker compose exec api ... y es el nombre DNS dentro de la red. El largo (lab11-api-solo-local) es el que ves en docker ps y te dice qué es sin abrir nada. Etiquetas en vez de comentarios: un comentario solo existe en el archivo; una etiqueta viaja dentro de Docker y se puede filtrar, como hiciste con --filter.

6

Entrar al client y mirar su mundo

Qué hacemos

Abrimos una shell dentro del contenedor client y miramos sus interfaces, rutas, vecinos y DNS.

Por qué

Antes de diagnosticar nada hay que saber cómo es "normal". Ese es el punto de partida de cualquier diagnóstico.

Si no lo hiciéramos

Sin conocer el estado normal no puedes reconocer lo que está mal.

Antes de ejecutar, predice

¿Cuál de las líneas de ip route será el gateway? ¿Esperas que ip neigh esté llena o vacía?

Esta es tu Terminal 1. La dejarás abierta durante todo el laboratorio.

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker compose exec client bash

Ya dentro, ejecuta los cuatro comandos:

Terminal 1 (dentro del client)
ip -br addr
ip route
ip neigh
cat /etc/resolv.conf
Qué debes observar

La interfaz eth0 tiene la IP 172.21.0.5. En ip route hay una línea que empieza por default via 172.21.0.1: esa es tu puerta de salida, el gateway. ip neigh es tu tabla ARP, y probablemente tenga pocas entradas porque este contenedor acaba de nacer. resolv.conf apunta a 127.0.0.11, el DNS interno de Docker.

7

Ver la decisión: entrega directa o por el gateway

Qué hacemos

Preguntamos al kernel qué haría para llegar a dos destinos distintos, sin enviar nada.

Por qué

Es exactamente la decisión que simulamos en clase, ahora hecha por tu sistema real.

Si no lo hiciéramos

Te quedarías con la teoría sin comprobar que el sistema real la sigue.

Antes de ejecutar, predice

¿Cuál de las dos respuestas incluirá la palabra via?

Terminal 1 (dentro del client)
ip route get 172.21.0.10
ip route get 8.8.8.8
Qué debes observar

Para 172.21.0.10 (misma red) la respuesta indica dev eth0 sin via: entrega directa. Para 8.8.8.8 (fuera de la red) incluye via 172.21.0.1: se entrega al gateway.

Por qué esto y no otra cosa

ip route get no envía ningún paquete, solo consulta la tabla. Herramientas como traceroute responden otra pregunta distinta (por dónde pasa el tráfico) y sí generan tráfico.

8

Ver ARP en vivo

Qué hacemos

Capturamos el tráfico ARP mientras tu máquina contacta por primera vez a otra.

Por qué

Verás con tus ojos la pregunta "¿quién tiene esta IP?" y su respuesta.

Si no lo hiciéramos

ARP seguiría siendo un concepto de dibujo, no algo que has visto pasar.

Antes de ejecutar, predice

¿Cuál será la MAC destino del primer paquete que sale? Pista: tu máquina todavía no la conoce.

En la Terminal 2 arranca la captura. Se detendrá sola tras dos paquetes. Las opciones: -n no traduce IP a nombres, para que veas los datos crudos; -e muestra las direcciones MAC; -i eth0 elige la interfaz; -c 2 captura solo dos paquetes.

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec client tcpdump -n -e -i eth0 -c 2 arp

Mientras espera, en la Terminal 1 contacta a una máquina con la que aún no hayas hablado:

Terminal 1 (dentro del client)
ping -c 1 172.21.0.30
ip neigh
Qué debes observar

El primer paquete es una pregunta del tipo who-has 172.21.0.30 tell 172.21.0.5, enviada a la dirección de broadcast (ff:ff:ff:ff:ff:ff). El segundo es la respuesta is-at con la MAC del dueño. Después, ip neigh muestra la entrada nueva para 172.21.0.30. Si no aparece ninguna pregunta ARP, esa IP ya estaba en tu tabla: usa otra IP con la que no hayas hablado, como 172.21.0.10.

Por qué esto y no otra cosa

tcpdump y no Wireshark: tcpdump está dentro del contenedor, ve exactamente la interfaz que nos interesa y funciona sin entorno gráfico. Wireshark desde Windows tendría que capturar en el puente de Docker, lo que complica el laboratorio.

9

Comprobar que la MAC destino es la del router

Qué hacemos

Enviamos un paquete a 8.8.8.8 y capturamos la trama para ver sus direcciones.

Por qué

Esta es la idea central de la lección 1.1. Aquí la compruebas en un paquete real.

Si no lo hiciéramos

Seguirías confiando en una frase que te dije, no en una evidencia tuya.

Antes de ejecutar, predice

La IP destino del paquete será 8.8.8.8. ¿A qué MAC crees que irá dirigida la trama: a la del dueño de 8.8.8.8 o a otra?

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec client tcpdump -n -e -i eth0 -c 2 icmp

Mientras espera, en la Terminal 1:

Terminal 1 (dentro del client)
ping -c 2 -W 2 8.8.8.8
ip neigh show 172.21.0.1
Qué debes observar

En cada línea de la captura aparecen dos MAC, una de origen y una de destino, y después la parte IP, con origen 172.21.0.5 y destino 8.8.8.8. Compara la MAC destino de la captura con la MAC que ip neigh show 172.21.0.1 asigna al gateway. Deben ser la misma. Es decir: la IP destino es la del servidor lejano y la MAC destino es la del router. Da igual si el ping recibe respuesta o no: lo que nos interesa es el paquete que sale.

Escalón 1: el nombre se resuelve, o no

Qué hacemos

Probamos un nombre que existe y uno que no.

Por qué

Es el primer escalón de la escalera. Si falla, no hay IP a la que hablar.

Si no lo hiciéramos

No distinguirías un problema de DNS de uno de red.

Antes de ejecutar, predice

¿Qué IP debe devolver dig +short web? ¿En qué escalón se detendrá el último comando?

dig devuelve 172.21.0.10. El primer curl imprime una pequeña página de laboratorio. El segundo termina con Could not resolve host y el código de salida 6. No salió ni un paquete hacia el servidor: la falla es de DNS.

Escalón 2: no hay camino

Qué hacemos

Intentamos conectar con 172.21.0.99, una IP que pertenece a tu red pero a ninguna máquina.

Por qué

Muestra un matiz importante: la ruta existe (dice "entrega directa"), pero el vecino no existe.

Si no lo hiciéramos

Pensarías que "no route to host" siempre significa que falta una ruta, y no es así.

Antes de ejecutar, predice

Según la tabla de rutas, 172.21.0.99 está en tu red. ¿Qué crees que ocurre cuando tu máquina pregunta por ARP quién tiene esa IP?

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec client timeout 8 tcpdump -n -i eth0 arp

Mientras captura, en la Terminal 1:

Terminal 1 (dentro del client)
nc -vz -w 10 172.21.0.99 80
ip neigh show 172.21.0.99
Qué debes observar

Tras unos segundos, nc imprime No route to host. La captura muestra varias preguntas who-has 172.21.0.99 sin ninguna respuesta. En ip neigh, la entrada queda en estado FAILED o INCOMPLETE. Sin MAC del vecino no se puede armar la trama. Es un fallo de la capa de enlace.

12

Escalón 4, silencio: el timeout de fw

Qué hacemos

Conectamos al puerto 9090 de fw, que está vivo pero tiene un firewall que descarta los paquetes.

Por qué

Es el caso más difícil de diagnosticar, porque no recibes ninguna respuesta que te guíe.

Si no lo hiciéramos

Sin comparar tres evidencias (la captura, el servicio y el firewall) no sabrías si el problema es la aplicación o la red.

Antes de ejecutar, predice

¿Esperas que nc te responda al instante o tarde? ¿Aparecerá algún paquete de vuelta en la captura?

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec client timeout 8 tcpdump -n -i eth0 tcp port 9090

Mientras captura, en la Terminal 1:

Terminal 1 (dentro del client)
nc -vz -w 4 172.21.0.30 9090

Ahora mira el otro lado, dentro del contenedor fw:

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec fw ss -ltn
docker compose exec fw iptables -L INPUT -n -v

Si la lista de reglas sale vacía, la regla pudo instalarse con el modo antiguo de iptables. Pruébalo así:

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec fw iptables-legacy -L INPUT -n -v
Qué debes observar

nc espera cuatro segundos y termina con timed out. La captura muestra varios paquetes [S] (peticiones de conexión) de tu client, repetidos con pausas cada vez más largas, y ninguna respuesta. En fw, ss muestra el puerto 9090 en escucha: el servicio está vivo. La lista de iptables muestra una regla DROP para el puerto 9090 con un contador de paquetes que crece en cada intento.

Conclusión: el servicio está sano, pero un firewall descarta los paquetes antes de que lleguen.

Por qué esto y no otra cosa

DROP y no REJECT: con REJECT, el firewall respondería activamente y recibirías un error inmediato. Con DROP no responde nada y se produce un timeout. En producción se prefiere DROP para no dar pistas a un atacante, y por eso los timeouts son tan comunes en problemas de firewall.

13

Escalón 4, rechazo: el refused de api

Qué hacemos

Conectamos al puerto 8080 de api, que escucha solo en localhost.

Por qué

Es el caso de diagnóstico más frecuente en el trabajo: un servicio levantado que no es accesible desde fuera.

Si no lo hiciéramos

No aprenderías a distinguir un rechazo de un silencio.

Antes de ejecutar, predice

Después del primer paquete [S] de tu client, ¿qué esperas que conteste la máquina api?

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec client timeout 8 tcpdump -n -i eth0 tcp port 8080

Mientras captura, en la Terminal 1:

Terminal 1 (dentro del client)
nc -vz -w 4 172.21.0.20 8080
curl -sS -m 5 http://172.21.0.20:8080/
echo "codigo de salida: $?"

Ahora diagnostica dentro de api:

Terminal 2 (WSL, carpeta del laboratorio)
docker compose exec api ss -ltnp
docker compose exec api curl -sS http://127.0.0.1:8080/
Qué debes observar

nc responde al instante con Connection refused. curl termina con el código de salida 7; el texto exacto del error cambia según la versión de curl, por eso confiamos en el código y en nc. La captura muestra un [S] seguido de un [R.] (reinicio de la conexión) que viene de 172.21.0.20: la máquina respondió activamente que no. ss muestra que el puerto 8080 escucha en 127.0.0.1 y no en 0.0.0.0. Desde dentro de api, curl sí funciona, así que el servicio está sano y el problema es dónde escucha.

14

Arreglar la api

Qué hacemos

Cambiamos la dirección en la que escucha, de 127.0.0.1 a 0.0.0.0, y recreamos solo ese contenedor.

Por qué

127.0.0.1 significa "solo yo, desde dentro". 0.0.0.0 significa "todas mis interfaces", incluida la que está en la red del laboratorio.

Si no lo hiciéramos

El servicio seguiría inaccesible desde otros contenedores.

Abre compose.yaml en VS Code, busca el servicio api y cambia "127.0.0.1" por "0.0.0.0" en su comando. Si prefieres hacerlo desde la terminal:

WSL, carpeta laboratorios/lab-1-1 del repositorio
sed -i '/api:/,/networks:/ s/"127.0.0.1"/"0.0.0.0"/' compose.yaml
grep -n -- '--bind' compose.yaml

Recrea solo la api y repite la prueba:

WSL, carpeta laboratorios/lab-1-1 del repositorio
docker compose up -d api
Terminal 1 (dentro del client)
nc -vz -w 4 172.21.0.20 8080
curl -sS -m 5 http://172.21.0.20:8080/
Qué debes observar

docker compose up -d api indica que recreó el contenedor api, sin tocar los demás. Ahora nc dice succeeded y curl devuelve la página del laboratorio.

Por qué esto y no otra cosa

0.0.0.0 o una IP concreta: ambas funcionan. En producción conviene limitar el servicio a la interfaz necesaria, porque 0.0.0.0 lo expone en todas las redes del servidor. Aquí la red es aislada, así que no hay riesgo. Publicar puertos con ports: no lo habría arreglado: publicar mapea un puerto del host al contenedor, pero el servicio seguía sin escuchar fuera de su propia loopback.

11. Diagnóstico de errores

Si algo no sale

Cannot connect to the Docker daemon

El servicio de Docker no está en marcha. En WSL sin systemd:

WSL
sudo service docker start

Con systemd, usa sudo systemctl start docker. Luego repite docker ps.

permission denied ... /var/run/docker.sock

Tu usuario no pertenece al grupo docker. Añádelo y abre una terminal nueva:

WSL
sudo usermod -aG docker $USER
Pool overlaps with other one on this address space

La red 172.21.0.0/24 choca con otra red tuya. Mira qué redes ya usas:

WSL
docker network inspect $(docker network ls -q) --format '{{.Name}} {{range .IPAM.Config}}{{.Subnet}} {{end}}'

Si hay choque, elige otro rango libre (por ejemplo 172.31.0.0/24) y cámbialo en todo el laboratorio: la subred y las cuatro IP en compose.yaml, y las IP de verify.sh. Las pruebas del laboratorio dan el mismo resultado con otro rango.

El build falla con "Temporary failure resolving deb.debian.org"

El contenedor de construcción no tiene DNS. Comprueba que WSL tiene internet (curl -sI https://deb.debian.org). Si WSL sí tiene, puede ser un problema del DNS de Docker. En ese caso cuéntame la salida completa del error y lo resolvemos.

El servicio fw termina con ERROR de firewall

Mira por qué:

WSL, carpeta del laboratorio
docker compose logs fw

Significa que el kernel o los permisos del contenedor no dejan instalar la regla. No sigas a ciegas: pégame esa salida y te preparo una alternativa para producir el timeout de otra forma. El resto del laboratorio sigue funcionando.

tcpdump: no suitable device found, o permission denied

La interfaz tiene otro nombre. Dentro del client ejecuta ip -br addr y usa el nombre que tenga la IP 172.21.0.5 en lugar de eth0.

La captura de ARP no muestra nada

Esa IP ya estaba en tu tabla ARP. Mira ip neigh y elige una IP que no aparezca, o espera a que la entrada caduque.

El texto del error de curl es diferente al que describe la guía

Es normal. El texto de curl cambia entre versiones. Lo que no cambia es el código de salida (7 para no poder conectar, 28 para timeout, 6 para no poder resolver el nombre) y el mensaje de nc, por eso los usamos para las comprobaciones.

verify.sh dice que un servicio no está en ejecución

Ejecútalo desde la carpeta del laboratorio, con el entorno levantado: docker compose ps debe mostrar los servicios en ejecución.
